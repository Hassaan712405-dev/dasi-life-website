# Issues and Improvements

This report separates **confirmed source-level behavior** from **potential risks contingent on external configuration**. No live database, RLS, deployment, or browser runtime was available for verification. Priorities are remediation order, not a claim that an exploit has been observed.

## Prioritized findings

| Priority | Classification | Finding and evidence | Recommendation |
|---|---|---|---|
| P0 | Confirmed functional defect | Guest checkout is presented and `createOrder` supports a missing user, but `proxy.ts` applies auth to `/checkout` and redirects users without a session to `/login`. | Remove `/checkout` from the auth-required branch if guest checkout is intended; preserve server-side price/stock validation and RLS protections. Test anonymous checkout through completion. |
| P0 | Confirmed architecture/integrity defect | `app/checkout/page.tsx` imports `createOrder` into a client component; `services/orders/orderService.ts` imports `createClient` from the browser client module. The documented price validation and stock check are therefore client-controlled, not a trusted server boundary. | Move order validation/writes into a server route/action backed by trusted server-side logic; validate product/variant ownership, active status, quantity and totals there. Keep any service-role use server-only. |
| P0 | Confirmed checkout consistency defect | In `orderService.ts`, failed `order_items` insertion is logged but creation continues; stock reduction errors and status-history insertion errors are not returned to the caller. The function can return success when the order has missing lines, unchanged stock, or no history. | Make order, line items, inventory changes and history one database transaction/RPC; return failure on any failure and ensure idempotent retry semantics. |
| P0 | Confirmed inventory race | `inventoryService.ts` reads stock and then writes `stock - quantity` without an atomic conditional update/transaction. Concurrent checkouts can both pass and overwrite each other. Cancellation restoration has similar read/write behavior. | Use a database transaction/RPC or atomic conditional update (`stock >= requested quantity`) with affected-row checks; test concurrent purchases and repeated cancel/status transitions. |
| P1 | Potential privacy/security risk; RLS-dependent | `order-success/page.tsx` and `track-order/page.tsx` request full order records (including address/contact fields) by order number from the browser. The order number generator is time-based with a short random suffix. `robots.ts` and `sitemap.ts` include `/track-order`. If anonymous SELECT is allowed to support these pages, order PII may be accessible by guessed/observed order number. RLS configuration is absent, so actual exposure is unverified. | Prefer a high-entropy, unguessable tracking token, return only minimum tracking fields, add throttling, enforce appropriate policies, and prevent private tracking URLs from being indexed. Verify with anonymous and cross-user tests. |
| P1 | Potential authorization risk; RLS-dependent | Admin services (`services/admin/*`) and admin pages issue database mutations using the browser anon client. Proxy/layout checks are client/request routing controls; no server-side authorization API is present. If RLS does not enforce admin membership for each operation, direct API calls could bypass the UI. Actual policy status is unknown. | Enforce admin role and ownership in RLS or trusted server endpoints for every read/write; test unauthenticated, customer, and admin roles independently. |
| P1 | Confirmed behavior gap | Checkout order service always writes `payment_method: 'COD'`; `serverDiscount` is always zero. Checkout collects no coupon and has `bankTransferEnabled` state without an implemented payment flow. No gateway integration was found. | If COD-only is intended, remove misleading options/state and accurately label payment. Otherwise implement provider-backed payment creation/verification, coupon validation and server-calculated discounts before advertising them. |
| P1 | Confirmed behavior gap | Homepage newsletter form only sets local `submitted` state and clears the input; no API, persistence, or email integration is connected (`components/layout/Newsletter.tsx`). | Connect a consent-aware subscription service and persist/manage unsubscribe preferences, or label the control as unavailable rather than implying enrollment. |
| P1 | Confirmed category-filter behavior bug | `ShopSidebar.tsx` changes query parameters only. On `/category/[slug]`, the page query uses the route slug, not the selected `category` query parameter; selecting another category/all products leaves displayed products unchanged. | Route category selections to `/category/<slug>` and “All Products” to `/shop`, while preserving price/sort query parameters. |
| P2 | Confirmed display/data inconsistency | `/shop` displays `products.length` filtered results but its “of” count queries all active products independent of category/price filters. Category result count also ignores price filter. | Count with the same predicates as listing, or remove/rename the total count label and use pagination/count semantics consistently. |
| P2 | Confirmed relevance defect | Product detail related-items query passes `categorySlug: product.category_id ? undefined : undefined`, which is always `undefined`; recommendations are not category-related. | Query by actual category ID/slug with an explicit service option; exclude the current product at query time if supported. |
| P2 | Confirmed configuration/feature mismatch | `settingsService.ts` models `shipping_enabled`, but checkout's displayed shipping calculation uses threshold/fee only. `orderService.ts` recalculates shipping independently and ignores `shipping_enabled`; default shipping threshold fallback behavior may yield free shipping. | Centralize shipping calculation in trusted code, apply `shipping_enabled` consistently and add tests for disabled, threshold zero, below threshold and above threshold. |
| P2 | Confirmed operational gap | Contact submission only inserts `contact_messages`; no email or notification delivery is wired. The admin notification service derives in-app notifications but does not send them. | Add monitored email/notification delivery (or clearly state response expectations are manual); add rate limiting, validation and spam controls. |
| P2 | Confirmed SEO/indexability concern | `/track-order` is explicitly included in `sitemap.ts` and is not disallowed in `robots.ts`. The page is a lookup surface that requests order/customer fields. Robots directives are not access control. | Remove tracking lookup from sitemap; set noindex and restrict the data response. Do not rely on robots.txt for privacy. |
| P2 | Confirmed observability weakness | Several services convert database failures to empty arrays/default settings or only `console.error` and continue. Examples include product/search reads, admin lists, settings defaults and order follow-up writes. Some admin handlers do not surface returned errors in UI. | Use explicit typed error results and user-visible retry/error states; distinguish empty results from failed requests; log operational context without customer secrets. |
| P2 | Potential stored-XSS surface | Product and organization JSON-LD are rendered via `dangerouslySetInnerHTML` with `JSON.stringify`. Product metadata may come from editable database fields. There is no `<` escaping in the visible serializer. Exploitability depends on who can write product data and CSP/RLS controls. | Serialize JSON-LD with a safe script serializer that escapes `<` (and other script-breaking sequences); test hostile product strings. Keep admin write permissions restricted. |
| P3 | Confirmed unused/misaligned dependencies | React Hook Form/Zod/resolvers and some configured package optimizations (e.g. `date-fns`, `lodash`) appear in manifests/config but no corresponding app usage was found in reviewed source. `getProduct.ts` exists but the principal detail flow imports from `getProducts.ts`. | Remove unused dependencies/config entries or adopt them consistently; maintain lockfile changes intentionally. |
| P3 | Confirmed missing automated verification | `package.json` defines `dev`, `build`, `start`, `lint`, but no test script or test files were found. No CI workflow/config was inventoried. This audit did not run build/lint. | Add tests for order totals/stock/role access, then CI typecheck/lint/build and critical route smoke tests. |
| P3 | Potential accessibility concerns | Visual labels often lack explicit label/input associations; interactive review stars and responsive menus need keyboard/screen-reader testing. Motion is reduced for users who request reduced motion, which is positive. | Add programmatic labels, focus management, visible focus states, keyboard testing and automated accessibility checks. |
| P3 | Potential performance/scaling concern | Shop/category fetch up to 100 records, dashboard/customer/admin services fetch whole collections and aggregate in JavaScript; dashboard retrieves all orders for metrics. | Add pagination, database aggregate/RPC queries, request caching and appropriate indexes after verifying actual schema and traffic. |
| P3 | Configuration hardening unverified | `next.config.js` disables the powered-by header and source maps, but no explicit CSP/security headers were found in the visible Next config. No deployment config is inventoried. | Define a tested security-header policy (CSP, frame/content-type/referrer policies) at the hosting edge/Next config, accounting for analytics and Supabase. |

## Additional observations

- Product pages provide metadata and structured data; dynamic sitemap includes active products but selects all categories without an active filter.
- Product cards/detail pages show compare-at prices and stock data, but a browser cart is not authoritative. Re-read all pricing/availability on the server before creating orders.
- `trackPurchase` reads an order by number and sends commerce details to analytics when enabled. Check consent and data minimization requirements for the operating jurisdictions.
- Product image upload code uses a public bucket URL. Bucket access, MIME/size restrictions and deletion permissions are external and unverified.
- Product/admin services frequently ignore secondary image/database write errors; operation success may not reflect complete persistence.
- Store/legal pages contain business/product claims as static copy. The audit verified source presence, not factual, regulatory or legal validity.

## Suggested remediation sequence

1. Reconcile guest checkout requirements with proxy gating.
2. Move order validation and mutations to a trusted, atomic server/database boundary.
3. Audit and test Supabase RLS and Storage policies, particularly orders, profiles, admin writes and contact submissions.
4. Minimize and protect order lookup data; remove it from sitemap and apply noindex.
5. Fix category navigation/counts and shipping/payment/coupon behavior.
6. Make errors visible, add operational tests/CI, then perform live staging checkout and accessibility/performance validation.

## Validation limits

This is a static source audit. Database credentials/values, customer information, existing log contents, and actual hosted records were not examined. No live exploit testing, deployment scan, build, lint, or end-to-end run was performed.
